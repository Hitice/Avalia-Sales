Plataforma

Plataforma de gestão e revenda de produtos

Uma rede de revendas vende placas com QR Code e NFC e serviços digitais pelo celular. O cliente paga por Pix ou cartão na hora, e estoque, comissões e financeiro são controlados no mesmo sistema.

Pedro Fernandes projetou, desenvolveu e opera a plataforma, do produto à infraestrutura.

Em produção em sales.avaliaone.com.br, com o código aberto.

O que está construído

Produto
Venda com vários itens numa cobrança, estoque de placas por lote, comissões e repasses, financeiro do revendedor, serviços executados pela operadora e a marca de cada revenda nas telas.
Engenharia
API e processamento em segundo plano em .NET, PostgreSQL com isolamento entre revendas no próprio banco e front em React para o celular do vendedor e o painel no computador.
Operação
Servidor próprio com Docker e Nginx, publicação pelo GitHub Actions com testes e aprovação, erros rastreados por versão e documentação no repositório.

Decisões técnicas e resolutivas

Cada decisão tem um ADR no repositório, com contexto, alternativas e consequências.

  • Isolamento entre revendas na API e no banco de dados

    Os dados de cada revenda ficam separados em duas camadas: se o filtro da aplicação falhar, o banco ainda recusa.

    Como funciona

    Filtro global do EF Core pela revenda do login e row-level security forçada no PostgreSQL. A aplicação conecta com um papel sem permissão de ignorar a regra, e um teste reprova a publicação se uma tabela com revenda ficar sem ela.

    ADR 0001Testes de isolamento

  • Pagamento confirmado na origem, no gateway

    A venda só é confirmada depois que o sistema consulta a cobrança no Pagar.me.

    Como funciona

    A cobrança é gravada antes de chamar o gateway, para nenhuma resposta se perder. O webhook só registra o evento; o Worker reconsulta a cobrança antes da baixa e trava a linha do evento, para o mesmo aviso não ser aplicado duas vezes.

    ADR 0004ADR 0005

  • Dinheiro em centavos e razão append-only

    Valores, taxas e comissões são inteiros em centavos, e cada movimento financeiro vira um lançamento no razão.

    Como funciona

    A aplicação só insere no razão: uma correção entra como estorno, não como edição. O mês fechado é travado por trigger no próprio banco, e a divisão em centavos sempre soma o valor cobrado.

    ADR 0011ADR 0020ADR 0003

  • Processamento assíncrono das integrações

    A API grava e responde sem aguardar e-mail, ERP ou contrato; o Worker processa as filas.

    Como funciona

    Os envios ficam em fila no PostgreSQL, processados a cada 10 segundos, com retentativa e espera crescente. Quando algo muda, o banco avisa a API (LISTEN/NOTIFY) e a tela recebe por SignalR.

    ADR 0013

  • White label com contraste calculado

    Cada revenda aplica logo e cor nas telas. A plataforma escolhe a cor do texto do botão e escurece o destaque até a leitura passar no critério do WCAG.

  • Migração incremental (strangler fig) com a operação ativa

    A plataforma nova assumiu as funções do sistema anterior rota a rota, e os dados foram migrados por importação validada em ensaio.

    Como funciona

    Cada rota do sistema anterior passou a redirecionar para a nova quando ela ficou pronta. O conversor lê o backup sem tocar no banco de origem; a importação roda antes em ensaio e, valendo, numa transação única, em que uma linha recusada desfaz o arquivo inteiro. O endereço impresso nas placas vendidas não muda.

    OperaçãoConversor

Verificação e qualidade

O que roda a cada publicação e onde conferir no repositório.

  • Testes automáticos

    Cerca de 475: 344 da API contra PostgreSQL real com o isolamento ligado, 116 do front, com acessibilidade conferida em cada componente documentado, e 16 jornadas ponta a ponta no celular e no computador.

    Testes da API

  • Publicação controlada

    O deploy só roda com o CI verde e aprovação manual, sobe as imagens do commit e confere a saúde da API pelo domínio. Rollback por nova publicação do commit anterior.

    Fluxo de publicação

  • Contrato entre front e API

    Os tipos do front saem do contrato OpenAPI da API, e o CI falha se estiverem desatualizados. Warnings do compilador são tratados como erro.

    Verificações do CI

  • Erros rastreados

    Erros da API, do Worker e do navegador chegam ao Sentry marcados com a versão publicada, o que liga cada alerta a um commit.

  • Segurança e dados pessoais

    Sessão curta com renovação rotativa, segundo fator, bloqueio por tentativas, cartão tokenizado no navegador, cabeçalhos de segurança na borda, auditoria das ações e exportação e anonimização dos dados do cliente.

  • Documentação com o código

    Regras do produto, arquitetura, operação e 20 registros de decisão versionados junto do código.

    Documentação
